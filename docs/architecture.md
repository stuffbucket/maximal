# Architecture

This is a local proxy that exposes the GitHub Copilot API as both an OpenAI-compatible and Anthropic-compatible HTTP service. It uses GitHub Copilot the same way Opencode's built-in Copilot provider does: authenticate with the user's own Copilot license, route requests to the Copilot endpoint, translate the response shape. The entry point is `src/main.ts` (CLI via `citty`), which dispatches to subcommands: `start`, `auth`, `setup`, `app`, `api`, `uninstall`, `check-usage`, `debug`.

## Request flow for `/v1/messages` (Anthropic path)

`src/routes/messages/handler.ts` is the core dispatch logic:

1. Rate limit check
2. Parse Anthropic payload
3. Detect subagent marker (`__SUBAGENT_MARKER__` in `<system-reminder>`, with opt-in `x-claude-code-request-class` / `x-claude-code-agent-type` hint headers as a fallback input) → sets `x-initiator: agent`
4. Detect compact requests (Claude Code context compaction via `x-claude-code-compaction` hint header or prompt heuristics)
5. Short-circuit Claude Code's tool-less startup "Warmup" request with a canned local reply — no upstream call (`src/routes/messages/warmup.ts`). Unrelated to the Claude Code *haiku tier*, which carries subagent tool calls and must stay tool-competent: see `src/lib/models/small-model.ts` `resolveSmallToolModel`
6. Merge mixed `tool_result` + text blocks to avoid fresh premium request
7. Normalize model ID → look up Copilot model
8. Route to one of three upstream flows:
   - `handleWithMessagesApi` — Copilot native `/v1/messages` (Claude models, preferred)
   - `handleWithResponsesApi` — Copilot `/responses` (GPT models)
   - `handleWithChatCompletions` — fallback for everything else

### Server tools in the loop

`planServerToolsForRequest` (`src/routes/messages/server-tools/`) runs after the request is classified and picks the tools to offer from the built-in web tools and the plugin gateway. `when-client-declares` tools are offered when `splitWebTools` found the matching Anthropic declaration. `always` tools are offered when the request is not a compaction or auto-continue, the client (`deriveUsageClient`) is one the tool allows, the client declared at least one tool of its own and did not set `tool_choice: none`, and no client tool has the tool's name (a collision skips ours and logs a warning). Subagent turns count; warmups never get here and `count_tokens` has its own handler. The declarations are added after the client's own tools, sorted by name from fixed definitions, so the `tools` array is byte-identical on every turn and the upstream prompt-cache prefix holds. Any planned tool sends the request through the loop (`web-tools/flow.ts`); a plan with an `always` tool takes the native Messages transport where the model uses `/v1/messages`, web tools alone keep their own transport and record no usage there, and an `always` plan records the summed usage under the transport's endpoint. The loop treats a `tool_use` of a planned tool as its own; a `hidden` call is executed and its `tool_use` and result never reach the client (streaming: the blocks are swallowed, take no client index, the intermediate `message_delta` is dropped and pings continue; buffered: the response is synthesized without them), while an `anthropic-*` call renders as `server_tool_use` plus its `web_*_tool_result`. A turn that also calls a client tool ends the loop and goes back to the client (our calls already ran); a loop that runs out of turns on hidden calls ends with `end_turn`.

## Errors on the inference routes

The inference route modules (`/v1/messages`, `/:provider/v1/messages`, `/chat/completions`, `/responses`) and the pass-through routes (below) mount the GitHub-token gate themselves and register `proxyErrorHandler(wire)` (`src/lib/errors/proxy-errors.ts`) as their Hono `onError`; handlers throw. The handler turns the error (`HTTPError` from the upstream, `CopilotAuthFatalError`, `NoUpstreamError` from the gate, or our own) into a wire-neutral reply, runs the wire's ordered rewrites (`proxy-error-rewrites.ts`: not signed in, upstream advice, context-overflow rewording, transient 5xx to 529, retry-header relay) and renders Anthropic's envelope or OpenAI's error object; `retry: "never"` becomes `x-should-retry: false`. A reply is always 4xx/5xx and a throwing rewrite is skipped. The upstream calls put the endpoint and model they sent on the `HTTPError` (`call`), so the advice can tell a model that doesn't serve the called endpoint (per the catalog's `supported_endpoints`) from one the plan lacks. Once a stream has started, `routes/messages/stream-error.ts` runs the same rewrites and writes an SSE `error` event. Other routes catch and call `forwardError`, which uses the same path plus one rewrite of its own (`upstreamTimeout`): a bounded GitHub read that times out answers `504` "GitHub didn't respond in time" instead of a generic 500. The inference routes keep their mapping. Wire details: [`spec/wire/auth-transport-wire-prd.md`](spec/wire/auth-transport-wire-prd.md).

## Pass-through routes

`/images/generations`, `/images/edits`, `/decisions` and `/systemone` (each also under `/v1`) dispatch a request to a model *operation* (`images.generations`, `images.edits`, `decisions`, `systemone`) through the plugin SDK's `OperationDispatch`, and relay the handler's JSON reply back unchanged: no translation, no streaming, no model mapping. The route factories (`createImagesRoutes`, `createDecisionsRoutes`, `createSystemOneRoutes`) take the dispatch as an injected `operations` dep. The routes are served by the `images`, `decisions` and `systemone` capability plugins (`packages/plugin-images`, `packages/plugin-decisions`, `packages/plugin-systemone`, kind `model`, on by default; see *Plugins*), reached through `pluginOperations` (`src/lib/plugins/gateway.ts`), which follows the running gateway. Each plugin binds client-facing model ids to a provider's models in its config (defaults: `gpt-image-2.5-flare`, `gpt-6-luna-decisions`, `microsoft-decision-1`, all on Copilot) and relays the body to the provider path of the same name (`/v1/images/generations`, `/v1/images/edits`, `/v1/decisions`, `/v1/systemone`), naming the provider's own model id; they serve the catalog's `image` and `decisions` models. A model the dispatch can't resolve throws `OperationUnavailableError`, which the OpenAI-wire error handler answers as `404 invalid_request_error / model_not_enabled` with `x-should-retry: false` (a plugin that is off, a model it doesn't bind, or no gateway at all; a model id the plugin's bindings don't name gets this 404 rather than Copilot's 400), before any rate-limit wait or approval prompt. `runOperation` (`src/routes/passthrough.ts`) is the one place that resolves, admits (rate limit, manual approval), dispatches and records usage. `recordOperationUsage` records against the request's `model` (endpoints `images`, `decisions`, `systemone`), because the replies name a different model or none, and carries the serving provider's id in `provider_name` (`source` stays `copilot` for Copilot). `GET /models` lists a `decisions`- or `image`-type catalog model only while some enabled plugin serves it (`src/routes/models/served-models.ts`). An image edit may be JSON or a multipart form; a form is re-sent as a form with a fresh boundary. Upstream errors take the inference routes' path above, in OpenAI's format; a served model the account lacks still gets the "not on your plan" advice.

## Middleware stack (in order)

`traceIdMiddleware` → `logger()` → `cors()` → `createAuthMiddleware` (API key validation via `x-api-key` or `Authorization: Bearer`; unauthenticated: `/`, `/status`, `/setup-status`, `/_debug/state`, the `/settings` and `/usage-viewer` redirects, and `/ui/*`; `/settings/api/*` always requires a key and refuses requests carrying a browser `Origin` that isn't Maximal's own (`http://localhost|127.0.0.1|[::1]:<the request's port>`; no `Origin`, as from CLIs and the shell's Rust calls, passes: `src/lib/auth/origin.ts`); `/mcp/*` applies the same key rules itself, loopback only; the dashboard's `/usage`, `/token-usage*` and `/_internal/*` endpoints trust loopback callers). The separate `requireGithubAuth` gate still protects `/usage` because it reads remote GitHub quota data; local `/token-usage*` history remains available while signed out. The list lives in `src/server.ts`.

## Model routing

`src/lib/models/models.ts` normalizes Claude model IDs via 5 regex patterns (handles variants like `claude-opus-4-6`, `claude-opus-4.6`). The `useMessagesApi` config flag (default `true`) controls whether Claude-family models use the native Messages API or fall back to Chat Completions.

`GET /models` lists every catalog model in OpenAI's shape. The Anthropic shape (Claude Desktop, the anthropic SDK) lists only models with a routable endpoint (`/v1/messages`, `/responses` or `/chat/completions`), and Codex's catalog only `/responses` models, so image, decisions and embeddings models stay out of both.

Root inference routes resolve the ordered, settings-driven `modelMappings` aliases after model-ID normalization and before live catalog lookup. See [`docs/dev/codex-integration.md`](dev/codex-integration.md) for exact/glob/regex semantics and the editable default alias. Root `/v1/messages` and `/v1/messages/count_tokens` then resolve normalized Haiku and Sonnet family identifiers through the selections in `anthropicMessages`; this Messages-only step is independent of `apps.claudeCode.enabled`, applies to every caller without guessing client identity, and is not used by `/responses`, `/chat/completions`, or provider-scoped `/:provider/v1/messages` passthrough.

Maximal maps direct Haiku and Sonnet aliases to concrete live-catalog IDs. When the Claude Code integration is enabled, it also projects those same selections into `ANTHROPIC_DEFAULT_HAIKU_MODEL` and `ANTHROPIC_DEFAULT_SONNET_MODEL`. These mappings are separate from Auto permission review. `CLAUDE_CODE_AUTO_MODE_MODEL` selects the client-side classifier that decides whether an action can run without asking; a generic Messages request carries no signal that would make this selection an inbound model alias. Automatic selection requires a non-embeddings, non-variant, tool-calling, streaming model on a routable endpoint (`/v1/messages`, `/responses` or `/chat/completions`), whether or not Copilot shows it in its picker: the Haiku alias prefers Haiku, then small GPT, then another GPT; the Sonnet alias prefers Sonnet, then full-size GPT, then small GPT; the permission classifier prefers a currently supported Haiku, then the configured or mapped GPT session model, then other GPT models. A still-eligible automatic choice stays put across catalog refreshes. Stable and explicitly zero-priced entries win later ties; Maximal never guesses latency or compares nonzero rates. Settings → Models can override any of the three. A saved override that disappears stays visible but is not substituted. Alias mappings with no automatic match leave inbound model IDs unchanged and, for enabled Claude Code integration, leave its environment keys unset so Claude Code's defaults apply; an explicitly reclaimed classifier stays fail-closed until a compatible model returns.

## App integrations

`src/apps/` owns filesystem detection, narrowly scoped configuration, durable intent, and boot/shutdown reconciliation for supported local clients. A new client implements `ClientApp` (`src/apps/index.ts`) and registers in `src/apps/registry.ts`; routes, the CLI and the shell stay app-agnostic. The Codex CLI and Desktop share one conservative user-level provider integration; its exact ownership and recovery contract is documented in [`docs/dev/codex-integration.md`](dev/codex-integration.md).

Claude Code is routed by an ownership-guarded `ANTHROPIC_BASE_URL` plus `apiKeyHelper` in `~/.claude/settings.json` (`src/apps/claude-code/`), reverted on shutdown and on the process `exit` event (`src/lib/start/shutdown.ts`). Enabling the integration projects the route-scoped Haiku/Sonnet selections and Auto permission classifier into that file with the same snapshot-and-marker ownership: pre-existing values and direct user edits (including deleting a setting) win until the person deliberately selects that setting in Maximal; that selection snapshots the latest external state and takes ownership. Maximal-owned values follow successful catalog refreshes. Shutdown restores the latest external values and suspends model ownership in a dormant journal so Automatic stickiness, explicit choices, and external divergence survive restart; explicit disable restores the same values and clears the journal. The toggle owns this base URL, helper, environment projection, and plugin MCP lifecycle; it does not enable or disable root Messages alias resolution. Don't reintroduce a PATH shim for `claude`. Turning the integration on or off also adds or removes the plugin MCP endpoints chosen for Claude Code (see *Plugins*).

## Config and state

- `src/lib/config/config.ts` — `AppConfig` shape, disk read/write of `config.json` in the app directory: `~/.local/share/maximal/` (Linux/macOS) or `%APPDATA%\maximal\` (Windows), resolved by `src/lib/platform/paths.ts`. `COPILOT_API_HOME` overrides it. A leading UTF-8 byte order mark (Notepad, PowerShell 5's `Set-Content -Encoding utf8`) is ignored, here and in the Claude Code and Claude Desktop files Maximal reads (`src/lib/platform/json-text.ts`). A `config.json` that isn't valid JSON leaves Maximal on the defaults, and `writeConfig` then refuses with `ConfigUnreadableError` rather than write over the file, until a read succeeds.
- `src/lib/config/config-schema.ts` — zod runtime validation. Bad config → exit non-zero with key path. Unknown keys → warning, kept via `.loose()`.
- `src/lib/runtime-state/state.ts` — singleton mutable state: tokens, accountType, rate-limit, models cache.
- `src/lib/auth/github-token-store.ts` — the GitHub identity store. Multi-account registry (schema v2) at `accounts.json` beside the legacy `github_token`: `{ activeKey, accounts: Record<"login@host", AccountRecord> }`, atomic temp+rename writes. Boot reads the active account; the legacy single-record file is migrated in once (gated, offline→`unknown@host`) and kept as a rollback fallback. The three sign-in producers (device-code, CLI, gh-reuse) all persist a typed `AccountRecord`; switch/remove + the `/settings/api/accounts` routes drive quick-switch (set active → reboot the sidecar into it). Sign-out forgets the active account; Remove forgets a specific one; both touch only maximal's own copy — never `gh`. RMW takes no lock (safe on the single Bun sidecar; see the comment above `addAccountToDefaultRegistry`).
- `src/lib/auth/secrets.ts` — file-based provider keys at `~/.local/share/maximal/secrets/<name>` (mode 0600). Env wins; file fills in unset values.
- `src/lib/runtime-state/cache.ts` — `Cache<K,V>` LRU wrapper with hit/miss/eviction metrics. Wrapped instances register globally for `/_debug/state`.

## Diagnostic surfaces

- **`maximal debug`** (and `--json`) — effective config (including `plugins_enabled`), executor selection (which `Executor` `selectExecutor()` would pick), secret sources (env/file/config/unset, never values), paths.
- **`GET /_debug/state`** — live equivalent on a running proxy, plus each plugin's lifecycle, status code and tool count. 404 by default; gated on `state.verbose`. Useful when restart isn't an option.
- **Daily log** at `~/.local/share/maximal/logs/messages-handler-<date>.log` — request payloads, translated SSE events, web-tools agent traces. 7-day retention.

## Token-usage sessions

The Dashboard keeps remote quota state separate from local observability state. `GET /usage` requires GitHub authentication and returns the shared `401 { error: "not_authenticated" }` contract while signed out; the Dashboard maps that code to an intentional account state rather than presenting transport text. Any other failure is "not available yet", never an error: the last good quotas stay on screen in muted ink under a quiet "Updated N minutes ago · reconnecting to GitHub" line, or, before the first good read, the usual layout shows placeholders under "Waiting for GitHub usage…". Every reason to re-read `/usage` goes through one refresher (`shell/src/dashboard/usage-refresh.ts`): showing the Dashboard view (always, at most every 15 s, since sign-in, sign-out and account switches happen in Settings and leave no other trace), the window coming back into view and new requests in the live token feed (each when the quotas aren't ready, are over 10 minutes old or belong to an ended period; at most every 15 s and 30 s), a quota period ending, and, after a failure while the Dashboard is in view, a backoff timer (30 s, 1, 2, then every 5 minutes; reset by a success or sign-out). One request is in flight at a time. Local `GET /token-usage*` history and sessions continue loading independently.

The Dashboard's live-flow graph and compact metrics, plus the peer Sessions view's table, share one frontend controller and one `GET /token-usage/sessions` poll (`src/routes/token-usage/route.ts`). The response shape is the zod schema in `src/lib/token-usage/sessions-schema.ts`, which the route parses before serving and the Dashboard parses on reading. It covers the last 24 hours of recorded requests whatever period the summary shows, plus the requests in flight now. Nothing is stored per session: `buildSessionsView` (`sessions.ts`) groups the stored rows by `session_id` on every call. Requests with no session id fold into one `other:<client>` group per client; they have no graph position or context meter.

**Stored per request.** Each `token_usage_events` row also records the client (`claude-code`, `claude-desktop`, `codex` or `other`, from the provisioned API key label, else the user agent: `client.ts`), the cache lifetime and whether the client asked for it (`cache_ttl_s`, `cache_ttl_requested`), whether it was a compaction, the context window numbers with their source, and when the request started (`request_started_at_ms`, the request context's `startTime`; `created_at_ms` is when its usage was recorded, at the end of the response). Migration step 2 adds these columns; the store also adds any of them missing on every open, so a database that ran step 2 before a column joined it catches up. Older rows read as client `other`, no cache, unknown window and no start time. Migration step 3 adds `plugin_id` for budget scopes (see *Budget limits*). The handlers fill them through `setRequestUsage` (`src/lib/http/request-context.ts`), using the helpers in `request-meta.ts`.

**Session id.** The affinity header wins, then the client's own id, then a fallback: `prompt_cache_key` for Responses (a Codex conversation stays one row), none for chat completions (no row per prompt).

**Several models in one session.** Claude Code sends subagent and side requests (often Haiku, often with no cache marker) under the parent's session id. So a session's cache and context come from each model's latest request, not from the latest request overall. The main model is the one with the most tokens in the session; the session shows its model and its context. The cache shown is the one that lasts longest among the models' latest requests.

**States.** A session is `streaming` while any request with its id is in flight, `warm` while `now < expires_at_ms`, and `cold` otherwise. Warm ends exactly at the expiry: a session at its boundary is cold. `expires_at_ms` is that cache's request completion time plus its lifetime. The Dashboard re-evaluates `warm` against its own clock every second, so a row goes cold without waiting for a poll.

**Client label.** `client_label` is the API key's label when the user named it. The labels the integrations provision (`claude-code`, `claude-desktop`, `codex`) only repeat the client's name, so they come back as null (`customKeyLabel` in `client.ts`).

**In-flight tracker** (`in-flight.ts`). `trackInFlight` is mounted in `src/server.ts` on the inference routes (`/chat/completions`, `/responses`, `/v1/chat/completions`, `/v1/responses`, `/v1/messages` and `/:provider/v1/messages`), after auth. It registers the request until its response body ends, errors or is cancelled, counting the delta text it passes through (`DeltaTextCounter`: the `text`, `thinking`, `partial_json`, `delta`, `content` and `arguments` strings of `data:` lines that carry a `delta` field, so neither SSE framing nor the events that repeat finished text count). Session id and model are read from the request context at list time, because handlers set them after the middleware runs. Entries older than 10 minutes are dropped as leaked, both when a request registers and when the list is read. Streamed characters divided by `STREAM_CHARS_PER_TOKEN` (4) estimate the tokens so far, which add to `flow_per_min`: the whole system's input, output and cache-creation tokens in the trailing 60 s. Cache reads are left out, so a turn that resends a large cached context doesn't read as flow. An entry with no session id counts as flow only. An entry whose session has no stored rows yet shows as a minimal streaming session until its first reply is recorded.

**Rate and live flow.** `rate_per_min` is the mean of the last 5 one-minute buckets; `rates` splits that window into input, output, cache-read and cache-write rates, and `model_rates` preserves the models used inside one session (including subagents). `minutes` holds the last 15 total-token buckets (`minutes.ts`), the same ones the summary uses. The Dashboard turns those rates into an OffscreenCanvas particle graph in a dedicated Web Worker. Endpoints sit on an inner rendezvous ellipse while their measured, center-anchored label blocks target the same angles on a separate outer ellipse. D3-force only nudges labels when their measured bounds collide with another label or a fixed endpoint/center obstacle; the rings and connections stay implicit, as in the American Time Use reference. Particle motion remains the worker's lightweight custom simulation inside the label ring. The first sessions poll establishes cumulative per-edge token baselines; later polls emit bounded one-trip bursts only for positive token deltas, so unchanged data is still rather than replaying a rolling-rate loop. WebFetch/WebSearch positions remain opt-in illustrative data because tool activity is not persisted.

**Cache lifetime** (`request-meta.ts`). Claude requests on the native Messages API: 5 minutes for any `cache_control` marker, 1 hour when any marker has `ttl: "1h"`, 0 when there is none. Responses requests: 5 minutes, or 24 hours when `prompt_cache_retention` is `"24h"`. A `/v1/messages` request served by a non-Claude upstream model (web tools, GPT) follows the Responses rule, because the upstream model decides what a marker does. Chat completions use 5 minutes.

**Cache confidence** (`CacheObservations` in `sessions.ts`, in memory, one instance for the route). A countdown is `estimated` for an automatic cache or a lifetime nobody asked for, `requested` when the client asked for the lifetime, and `observed` once a resume proved it. A resume is a request on the same model that started more than 5 minutes after the previous one completed, and within the lifetime it asked for. The gap runs to the resuming request's start, so a request that reached a 4-minute-old cache and then ran for two minutes proves nothing. A request with no recorded start makes no resume. A resume that reads back at least half of the previous request's context (input plus cache read plus cache creation) is a hit; anything less is a miss, because a shared prefix (tools, system prompt) can stay cached when the conversation's own cache is gone. After 2 consecutive misses for a model, a lifetime over 5 minutes is cut to 300 s, `cache.downgraded` is true, `cache.downgraded_from_s` holds the lifetime that failed, and confidence is `estimated`; one miss can be an ordinary eviction. A later hit restores the model. Each resume is counted once, by the pair of rows it came from, so repeated polls over the same rows don't recount it. The Sessions view prefixes any countdown that isn't `observed` with "about".

**Context window** (`resolveContextWindow` in `request-meta.ts`). The ceiling is always Copilot's `max_prompt_tokens`. The window depends on the client: Codex uses its catalog entry's `context_window` (and its compaction limit, or Maximal's own threshold when Maximal compacts), falling back to the model listing when the model has no entry; Claude Code with the `context-1m` beta uses 1,000,000; everyone else uses the listed window (`max_context_window_tokens`, else `max_prompt_tokens`, the value `/v1/models` serves). Each row says which in `window_source`. Used tokens are the main model's latest request's input plus cache-read plus cache-creation tokens. The table's meter fills against the limit, the smaller of the window and the ceiling, so its fill, percent and warning steps agree. When the ceiling is the lower one, the tooltip names both: "{used} of {ceiling}, Copilot's limit ({window} is {source})". A compaction point below the limit gets a tick on the meter and a tooltip line of its own.

**Polling.** `shell/src/dashboard/live/controller.ts` polls every 2 s while the page is visible and gives up a read after 10 s, so a hung request can't stop the polling. A failed or invalid read keeps what is on screen and shows the error in the graph. It also ticks once a second for countdowns. The metrics, graph and table render into fixed hosts that the page's string renders never touch, so selection, hover and the open "Chat and completions" section survive polls and re-renders.

**Table** (`table.ts`, `rows.ts`). Columns: client, session (model, start time, short id), state (streaming, warm with a countdown, or cold with the time its cache ran out; a downgraded model names the lifetime that didn't hold), tokens/min, context (a meter plus percent, the quota meter's 75% warning and 90% error steps, and when it last compacted), last request, total. Countdowns read m:ss under 10 minutes, whole minutes under an hour, then whole hours. Times from a day other than today carry a short day name. Streaming and warm sessions come first, busiest first, then a "Cache cold" divider and the 20 most recent cold ones, with a "Show N more" button for the rest. A row is refilled only when its session or locale changed, or when it shows something that reads the clock (a warm countdown every second; "compacted N min ago" and day names every minute).

## Budget limits

Spend limits are plain caps on spend, configured in `config.json`'s `budget` block (`src/lib/budget/schema.ts`, validated as part of `AppConfig`). A limit applies to any model and exists only when someone creates it; `budget.enabled: false` switches enforcement off and keeps the limits. Enforcement is below, under *Budget enforcement*.

- **A limit** has an `id`, an optional `label`, a `scope`, a `limit` in nano-AIU, a `limitReset`, a `warnAt` fraction (default 0.8) and an `action` (`block` or `warn`). There is no limit until someone creates one; no rows exist per model.
- **Scope.** `global` covers every recorded request. `key` covers one client key: the API key's label, else the client recognised from the user agent (`claude-code`, `claude-desktop`, `codex`), else `unidentified`. `plugin` covers a plugin or built-in capability through the usage row's `plugin_id`; the `/images`, `/decisions` and `/systemone` routes record their endpoint as their capability. `provider` covers `copilot`, or a configured provider by name.
- **Spend** is `SUM(total_nano_aiu)` from `token_usage_events` over the scope's rows in the period (`src/lib/token-usage/spend.ts`), so a limit counts spend recorded before it existed. Migration step 3 adds `plugin_id` (back-filled for the capability endpoints).
- **Periods** (`src/lib/budget/periods.ts`). `daily` and `weekly` reset at 00:00 UTC, weeks starting Monday; `never` is a lifetime cap. `{ "follow": "<provider>:<window>" }` runs from the window's previous reset to the `resetsAt` the provider last reported, so a reset that moves forward starts a new period. A rolling window runs its `durationMs` back from the reset. With no earlier reset on record, a fixed window's period starts one calendar month before its reset. A reset that has passed with no newer report rolls forward by the last cycle length. Each of those guesses is flagged `reset_estimated`, and a window with no usable reset, or none reported yet, falls back to `daily` (`reset_basis: "fallback"`).
- **Provider quota windows** (`src/lib/budget/provider-windows.ts`). A provider reports zero or more windows, normalised to `ProviderQuotaWindow`. The registry keeps the latest per `provider:id` and the reset before it, in the token-usage database's `provider_quota_windows` table (migration step 4), so both survive a restart; reports that arrive before the stored windows load wait for them. The Copilot adapter (`copilot-windows.ts`) reads one window per `x-quota-snapshot-<id>` header in `finishUpstreamResponse` (every Copilot reply, errors included) and one per `quota_snapshots` entry when `GET /usage` fetches `/copilot_internal/user`. Window counters lag real spend and are shown for context only; limits count local `total_nano_aiu`.
- **Units** (`src/lib/budget/units.ts`, the only place costs change unit). Amounts are stored as integer nano-AIU (10⁻⁹ AI credit). They are shown in US dollars by default at $0.01 per AI credit, or in AI credits (`budget.display.unit`). `budget.display.creditUsd` overrides the rate and changes only what is shown.
- **API** (`src/routes/settings/budget.ts`, contracts in `settings-types.ts`). `GET /settings/api/budget` returns `BudgetStatusResponse`: each limit, widest scope first, with OpenRouter's `/api/v1/key` field names (`limit`, `limit_remaining`, `limit_reset`, `usage` for the current period, `usage_daily`, `usage_weekly`), `period_start`, `resets_at`, `state` (`ok`, `warning` at `warnAt`, `exhausted` at the limit), the same amounts in the display unit, the `effective_budget` (the blocking limit already spent, else the one with the least room), and the provider windows. `PUT /settings/api/budget/limits/:id` creates or replaces a limit from `limit` (nano-AIU) or `amount` (display unit); `DELETE` removes one. `PATCH /settings/api/budget` sets `enabled` and `display_unit`. Every change replies with the new status and pushes it as a `budget.changed` event on `/settings/api/events`; a bad id or body is a 400 `validation_error`, an unknown id on delete a 404. Each limit also reports `held` (nano-AIU reserved by calls in progress). `GET /settings/api/budget/activity?period=day|week|month&group=model|plugin|key|provider|day` returns `BudgetActivityResponse` (spend and request count per group since 00:00 UTC today, Monday or the 1st; groups that spent nothing are left out) and `GET .../activity.csv` the same rows as CSV.

## Budget enforcement

`src/lib/budget/service.ts` holds the logic with every dependency injected (clock, config, store, provider windows, usage stream); `runtime.ts` wires the app's instance (`getBudgetService()`).

- **Check and hold.** A caller about to make a billed call `reserve`s an estimate. Every limit whose scope covers the call is checked: spent + held + estimate must fit. A call with no estimate (chat, decisions, SystemOne, and server tools that declare none) is admitted while spent + held is under the limit, so it can go over by what is in flight. An admitted call holds its estimate until it commits (the usage row it records carries the real `total_nano_aiu`; a reply with no cost is booked at the estimate) or releases (the call failed before it was billed, or was abandoned). The check and the hold are one synchronous step, so concurrent callers can't claim the same room.
- **Spend ledger.** Spend has one source, `token_usage_events`. Each limit keeps an in-memory entry for its current period, loaded from the database when the period starts (or its scope or followed window changes) and kept current from the usage rows recorded after (`onTokenUsageEvent`), so a check never waits on the write queue. A `block` limit refuses, a `warn` limit never does; either warns once per period when a call crosses `warnAt` (a log line and `budget.changed`). Scopes are `global`, a client key (the API key label, else the recognised client, else `unidentified`), a plugin or built-in capability (`images`, `decisions`, `systemone`, from the row's `plugin_id`) and a provider (`copilot`; every usage row carries `provider_name`).
- **Holds in the database.** A hold that reserves something is written to `budget_holds` (migration step 5) and closed on commit or release. At start, holds a crash left open become `orphaned` and count against their period at the estimate; closed ones are pruned after 7 days. With no usage database nothing persists and limits hold within one run.
- **Enforcement points.** `runOperation` (the pass-through routes) holds around `dispatch` through `dispatchWithBudget` (`src/lib/budget/dispatch.ts`); image calls are estimated from quality and count (`estimate.ts`). The chat handlers (`/v1/messages`, `/chat/completions`, `/responses`) call `admitChat` after the rate limit, gate-only. The plugin server-tool listings reserve under `{ operation: "server_tool", plugin, tool }` before `callServerTool`; a billed tool declares `estimate(input)` (the model operation and body to price, so `generate_image` holds the image estimate, not 0) and reports what the provider billed with `call.reportSpend`, which records the usage row (`recordOperationUsage`) and commits the hold (`bookedResult`, shared with `dispatchWithBudget`). The `/:provider/v1/messages` routes are not gated.
- **At the limit.** A `BudgetExceededError` (`errors.ts`) is rendered by `proxyErrorHandler` as 402: Anthropic wire `billing_error`, OpenAI wire `insufficient_quota` with `code: "budget_exceeded"` and the figures in `error.metadata`, `x-should-retry: false`, `Retry-After` when the reset is within a day. A refusal caused only by other calls in flight omits `x-should-retry` and sends `Retry-After: 5`. A refused server tool is not an error of the turn: the model gets an `is_error` tool result, `Not run: <the sentence> Don't retry this tool until the budget resets or is raised.`, and the tool's description never changes (the prompt cache holds).

## Never block the event loop

The proxy is one Bun process with one event loop. A synchronous child process (`execSync`, `execFileSync`, `spawnSync`, `Bun.spawnSync`) holds every in-flight request until the child exits, streaming `/v1/messages` responses included. Settings once ran `npm prefix -g`, `claude --version`, and several `claude mcp add-json` calls this way, inside request handlers, which stalled live traffic for seconds per toggle.

- **Run programs with `runFile()`** (`src/lib/system/run-file.ts`). It never rejects: exit code, output, and `notFound` come back in the result. The `blockingSpawnGuard` lint rule (`eslint.config.js`) bans the synchronous forms in `src/`, except three files that run only before the server listens or in a CLI command.
- **Cache what detection learns.** `npmGlobalPrefix()` shares one spawn across concurrent callers and keeps the answer (a miss is retried after a minute). Synchronous detection reads `cachedNpmGlobalPrefix()` and never spawns. `readClaudeVersion()` caches by binary path and modification time. Settings polls these lists, so a repeat call must be file probes and cache hits.
- **Async work that used to be serialized by blocking still needs serializing.** Queue passes per target so two toggles can't interleave external CLI calls for one entry, and have each pass read config when it starts.
- **Shutdown is the one synchronous exception.** The `exit` safety net can't await, so cleanup there edits files only.
- **Synchronous file reads can block too.** With endpoint security that scans on open (e.g. Microsoft Defender), the first read of a recently written file can take hundreds of milliseconds. The request hot path is clear (config is cached, logs use streams); Settings code still reads client configs synchronously.

## Parallel-agent convention

This repo can collide on a shared working tree (lint-staged stash + concurrent merge ate a turn already). For parallel agents:
- **Spawned subagents:** pass `isolation: "worktree"` to the Agent tool.
- **Sessions:** create a worktree with `git worktree add .claude/worktrees/<task> -b <type>/<task> origin/main` (`<type>` is the Conventional Commit type the work will land as); clean up with `git worktree remove .claude/worktrees/<task>` after merging back. `git worktree add` does **not** run `bun install`, so the gitignored `src/generated/ui-embed.ts` stub won't exist — the gates now self-heal it (`check:fast` and the test preload call `ensure:ui-embed`), but run `bun install` in the new tree anyway if you need its node_modules.
- **The primary checkout sits detached at `origin/main`; no worktree checks out `main`.** A branch can be checked out in only one tree, so a worktree holding `main` strands the primary checkout on whatever feature branch it last had, and that branch goes `[gone]` the moment its PR merges. Refresh with `git switch --detach origin/main`.
- **Tidy branches with `bun run git:tidy`, never `git branch -D`.** It never touches a branch checked out in any worktree, one with an open PR, or one committed to in the last 14 days; it deletes branches whose tip is already in `origin/main` and archives the rest (remote → pushed tag `archive/<branch>/<sha7>`, local → local-only `refs/archive/<branch>/<sha7>`) before removing them, so nothing is lost. Dry run by default; `--apply` to act.
- **Reusing a branch for a follow-up PR?** Land the first PR with a merge commit (see *Release & PR conventions*). A squash leaves the branch's commits outside `main`, so the next PR from that branch re-shows the old diff.
- **Never run `git stash pop` in a shared working tree.** It silently merges another in-flight worker's stash into your tree, and on conflict it leaves an inconsistent state that's easy to "clean up" by `rm`-ing files that aren't yours. We lost a session's worth of React-shell work to this exact path: a subagent ran `git stash pop` to bisect a test failure, hit a conflict, and `rm`'d untracked files it didn't recognize. If you need an isolated bisect, use a worktree (see above). If you must inspect a stash, use `git stash show -p stash@{N}` (read-only) and never `pop` / `apply` outside an isolated tree.
- **Stop after two follow-up commits for the same CI failure** and surface it instead of trying a third guess.
- **`check:deep` passing does not prove a UI change works** — render it (the `ui-layout-verification` skill) before calling it done.

## Testing gotchas

- **Tests run inside a cross-platform user sandbox.** The global preload
  overwrites POSIX, XDG, Windows app-data, Maximal, Claude, and temp-directory
  environment variables before application modules load. It also normalizes
  Bun's cached `os.homedir()` result and provides the same environment to child
  processes. Destructive functions must still accept explicit fixture paths;
  the sandbox is defense in depth. Desktop startup and uninstall never edit
  shell profiles or PATH registries, and package managers/installers own CLI
  exposure and removal. See [`dev/testing-strategy.md`](dev/testing-strategy.md)
  §4.
- **`mock.module` persists forward across files in a run — now lint-enforced.**
  Bun does not reset module mocks between test files, and CI orders files
  differently than local, so an unrestored mock leaks its stub into a
  *sibling* file that then reads stale state — the classic "green locally,
  red on CI" (or vice-versa) failure. This bit us **four times** (the last
  cost a long #229 debugging loop), so an ESLint rule (`mockModuleLeakGuard`
  in `eslint.config.js`, scoped to `tests/**`) now **bans the fire-and-forget
  forms**: `void mock.module(...)` and a bare `mock.module(...)` expression
  statement both error.
  - **Awaited is *not* automatically safe.** `await mock.module(...)` passes
    the lint rule, but an awaited `afterAll` *restore* does **not** reliably
    land before the next file's static imports on CI — so a module mock that
    intercepts a *shared* module still leaks across files even when restored.
    The rule catches the common footgun, not this one.
  - **Restore from a snapshot, not the live namespace.** `mock.module`
    patches the module's namespace object in place, so
    `const real = await import(m)` followed by
    `mock.module(m, () => real)` "restores" the stub (so does
    `() => ({ ...real })`, and `import * as real` is the same object). Capture
    `{ ...(await import(m)) }` before mocking. The `local/mock-module-snapshot`
    rule (`eslint-rules/mock-module-snapshot.js`, wired into
    `mockModuleLeakGuard`) errors when a `mock.module` factory reads a live
    namespace. A leaked no-op `sleep` from
    `tests/poll-access-token.test.ts` once turned an orphaned device-code
    poller into an endless promise loop that hung CI. Per-test timeouts can't
    stop that, so `tests/helpers/starvation-watchdog.ts` kills the run after
    60s without an event-loop turn.
  - **The durable fix is to not mock a shared module across files at all.**
    Prefer the **real** module (the test preload redirects `COPILOT_API_HOME`
    to a temp dir, and `getClaudeCodeSettingsPath()` honors `CLAUDE_CONFIG_DIR`
    — so config/settings round-trips are already isolated), or **injectable
    function options**. Only stub a module with no env/injection seam, keep the
    wrapper behaviorally identical (spread `...actual`, forward `...rest`), and
    prove via a sequential-import repro that it can't break a later file.
- **Green tests can still test nothing.** Mutation testing (`bun run mutate`)
  caught classification tests that passed without exercising the branch
  they claimed to cover (the fixture hit a different code path that
  returned the same value). For security-critical or branchy logic, run
  Stryker and confirm the targeted mutants actually die — don't trust a
  passing assertion alone. Every surviving mutant must land in exactly one of
  three buckets — **killable** (write the test), **dead** (delete it / encode
  the impossibility in types), or **proven-equivalent** (written proof + reason
  to keep). See [`dev/testing-strategy.md`](dev/testing-strategy.md) §6 for the
  disposition rule and the hot-path modules that warrant periodic sweeps.

## Release & PR conventions

- **Release is driven by Conventional Commit *types*.** release-please
  scans commits since the last tag; only `feat:` (minor) and `fix:`
  (patch) cut a release. `test:`/`chore:`/`ci:`/`docs:`/`refactor:` are
  release-silent. If release-please "isn't doing anything," it almost
  certainly found no `feat`/`fix` commit — check the `release-pr` step
  log for `No user facing commits found ... skipping` before assuming
  it's broken.
- **`main` accepts squash and merge commits; pick per PR.**
  - *Squash* (default for one-shot PRs): the PR **title** becomes the
    commit subject and the PR **body** its message (repo setting
    `PR_TITLE`/`PR_BODY`; it used to take a single-commit PR's commit
    subject instead, which is how the `chore:` PRs #481/#483 landed as
    `fix:`). The branch's own commits never reach `main`.
  - *Merge commit* (for a branch that keeps living, or whose commits
    each matter): every branch commit reaches `main` and release-please
    reads each one; the `Merge pull request …` subject itself is ignored.
    Afterwards the branch's tip is in `main`, so it can carry a follow-up
    PR and `git:tidy` deletes it losslessly.
- **Every subject release-please can see must be one valid Conventional
  Commit** (`fix: …`, not `test+fix: …` — that parses as one unrecognized
  token and release-please skips it, even if the diff holds a real fix).
  The `commit-msg` hook (`scripts/check-commit-msg.ts`, installed by
  `bun install`) checks each commit locally; CI's `test` job checks the
  PR title and every commit on the PR. CI reads the title when the PR is
  opened or pushed to, so after retitling, push or re-run CI.
- **Auto-merge is on; `main` does not require branches to be up to date.**
  Queue a PR with `gh pr merge --auto --squash` (or `--merge`) and move on.
  CI also runs on every push to `main`, which catches two PRs that pass
  alone but break together.
- **What a release ships.** `release.yml` attaches the raw binaries (macOS,
  Windows, Linux x64/arm64), the Windows installers, the macOS DMG and
  updater bundle, and the Debian packages (`maximal_*` and
  `maximal-desktop_*`, amd64/arm64, smoke-tested on Debian 13 and Ubuntu
  24.04/26.04), then publishes. Merging the updates-manifest PR redeploys
  mxml.sh, which also rebuilds the signed apt repository from the tags the
  manifest names. Checklist: [`release-runbook.md`](release-runbook.md).

## Tauri shell

`shell/` is a Tauri 2 menu-bar app that wraps the proxy for non-CLI users. Rust ownership is split once along the process/presentation boundary: `shell/src-tauri/src/sidecar_runtime.rs` owns profile and app-data policy, ports, authenticated readiness, process generations, lifecycle, sidecar-managed status, dynamic capabilities, and presentation-neutral HTTP transport; `shell/src-tauri/src/lib.rs` composes that runtime into Tauri and owns plugins, commands, polling-driven native presentation, tray/windows/splash/notifications, and updater presentation. Runtime outcomes cross that boundary as neutral events, so the sidecar module never calls native presentation helpers. `bun run app:sidecar` builds the UI (`bun run build:ui`), regenerates the embed manifest, and compiles the standalone proxy into `shell/src-tauri/binaries/`. The shell always forces its sidecar to `127.0.0.1`; production keeps the compatibility port 4141, while `bun run app:dev` asks the OS for a port on first launch, persists it in the profile, and reuses it so the webview origin and local storage stay stable. A nonce-bound stdout readiness record gives Rust the actual port before it registers an exact runtime capability or opens a remote webview. Each worktree has a stable profile ID in its Git admin directory, producing a D-Bus-safe Tauri identifier and platform-native app-data directory; an explicit `COPILOT_API_HOME` is resolved and used instead. Before launch, the runner uses that profile's session sentinel to stop its prior sidecar and wait for both the sidecar and parent shell, without scanning ports. `bun run app:build:test` uses the fixed non-production identifier and product name from `tauri.test.conf.json`; development and test profiles do not register or query production updater surfaces. The standalone CLI still owns `HOST` when it starts the proxy directly. The Settings shell (React, Bun-bundled) and observability UI (vanilla) live in `shell/ui/{settings,dashboard}` and are **embedded in the sidecar binary**, served by the proxy at `/ui/settings` and `/ui/dashboard` (`src/routes/ui/route.ts`); `/ui/sessions` selects the same observability bundle's Sessions view. Dev reads `shell/dist` from disk and production reads `$bunfs`. The single webview switches among those three surfaces while preserving observability state. The outer `WebviewWindow` is the one-webview construction wrapper; its underlying native `Window` owns geometry and constraints, while the Dashboard/Sessions surface remains an HTML iframe rather than another Tauri webview. The official `tauri-plugin-window-state` plugin tracks only its `settings` label and only inner size, outer position, and maximized state; the `1100×720` builder size is a centered first-launch fallback. Automatic restoration is skipped in favor of a controlled hidden restore after the plugin's window-ready hook; restoration and physical work-area repair run off the main event loop and keep inner and outer dimensions distinct. Constraints remain logical and surface-aware: Settings bounds only useful width, Dashboard/Sessions remove maxima, and maximized windows defer constraint mutation until they return to normal size. Visibility is platform-owned: macOS/Linux close managed windows back to the menu bar/tray. Windows creates the restored unified window only after the sidecar origin is authorized, shows it minimized with `SW_SHOWMINNOACTIVE` so the default taskbar button exists without stealing focus, and lets explicit actions or first-run account setup present that same window. Windows X asks for confirmation before starting bounded sidecar/configurator shutdown and quitting the app. Decorations and fullscreen are not restored. macOS status items use black-and-alpha AppKit template images so the system supplies the current appearance and selection color. Windows uses a contrast-safe full-color notification-area icon and publishes stable Dashboard, Sessions, Settings, update-check, logs, and config actions in the taskbar Jump List; those links route through the single-instance process just like native tray actions. Legacy `/settings` and `/usage-viewer` 301-redirect to the embedded UI. No Vite — Bun is the bundler.

- **Windows sidecar containment.** Maximal owns a local path patch of `tauri-plugin-shell` 2.6.0 under `shell/src-tauri/patches/`. Its Windows spawn remains race-free: the child is created suspended, its Job Object is configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, the child is assigned, and only then is it resumed. The shell holds the Job Object handle, so normal exit, updater `exit(0)`, and forced shell termination all close the lifetime boundary and the kernel ends the sidecar's non-breakaway process tree. The native Windows shell tests compile the exact patched module and verify that closing the Job Object terminates a synthetic child and its descendant; they never discover or signal an installed Maximal process. The GitHub-hosted packaged-app smoke seeds isolated Claude Code and Codex files, verifies boot applies both configurators, reinstalls while the app is running and requires the exact old shell and sidecar to exit, then verifies a replacement reaches `/status`. Its primary shutdown first proves ordinary startup creates a minimized, non-activating taskbar window, then routes a Dashboard task through the single-instance process and confirms the same window is restored. It sends `WM_CLOSE`, requires the shell and sidecar to remain alive behind the app-styled confirmation, accepts that prompt through Windows UI Automation, and then proves Windows X-close performs scoped configurator cleanup, preserves routing intent, and exits the exact shell and sidecar processes. A separate abrupt test force-terminates only its captured shell PID and requires the exact sidecar PID and listeners to disappear before any installer hook can perform image-wide cleanup.
- **New settings sections are React islands:** `shell/src/ui/islands/<name>-island.tsx` mounting `shell/src/ui/features/<name>/`; hash-nav section routing stays in `shell/src/main.ts`.
- **Updates.** The sidecar decides whether to offer one (`src/lib/update/update-check.ts` reads `https://mxml.sh/updates/manifest.json`; never github.com), which shows the topbar "Update to X.Y.Z" button and the tray item. On Windows and macOS both install in place (`IN_PLACE_UPDATE` in `shell/src-tauri/src/lib.rs`): the shell checks `https://mxml.sh/updates/desktop/<channel>.json` with `tauri-plugin-updater` (the channel comes from the app's version: `X.Y.Z` is `stable`, `X.Y.Z-rc.N` is `rc`), asks the user with a native confirm naming the version, downloads the update and verifies its signature against `plugins.updater.pubkey` and the signed version, then installs and relaunches. On Windows it stops the sidecar first, ends any `maximal-mcp-broker.exe` an older version left running, and runs the NSIS installer, which relaunches Maximal. The NSIS installer and uninstaller end them again first (`shell/src-tauri/windows/hooks.nsh`), as the MSI and `install.ps1` do; no current build ships that file. On macOS the plugin swaps the `.app` bundle (asking for an administrator password if its folder isn't writable), then the shell stops the sidecar and relaunches. A macOS app that can't replace itself (run from the disk image, from App Translocation, or outside a bundle) skips straight to the fallback. Any failure says so in a native dialog and opens mxml.sh. Linux never installs in place: the Debian/Ubuntu packages update with apt. An apt install (`/usr/bin/maximal` with the package's `/usr/lib/maximal/installed-by-apt` marker; `src/lib/update/install-source.ts`) gets `update_command` in the update status, so the button and the tray item read "Update with apt" and open Settings → Diagnostics, which shows the command to copy; Maximal never runs apt. The shell's background poll shows its "update available" OS notification once per version, across restarts: the last version announced is written to `update-notified` beside the `locale` file (before the notification fires; a failed write is logged and the notification still shows), so launching again while still behind doesn't repeat it. **Check for updates.** The sidecar caches its check for 6 hours; the tray's "Check for updates" item and Settings → Diagnostics' "Check now" button ask for a fresh one with `GET /settings/api/update-status?force=1` (same response shape). The check rate-limits itself: at most one real fetch per 30 s (`FORCE_MIN_INTERVAL_MS` in `update-check.ts`), and a forced check inside that window returns the last result. A real fetch is still a conditional request (ETag), so it costs a 304 when nothing changed. The tray item (always shown beside "Update to X.Y.Z") runs the check through the shell's update-status path (`parse_update_status`), updates the tray item, tells the Settings window to re-read (`update:status` event), and shows a native dialog: "Maximal is up to date (X.Y.Z)", a plain failure message (an answer with `last_error` is a failure even if an older result is known), or that update checks are off. "Check now" calls the same URL from the page, then `refresh_update_status` has the shell re-read the cached result so the tray agrees. `maximal start` also logs one line when a newer version is out (with the apt command for an apt install), and `/status` reports the last check. Release signing, the manifests and the apt repository: [`release-runbook.md`](release-runbook.md), [`decisions/site-runtime-version-manifest.md`](decisions/site-runtime-version-manifest.md), [`linux.md`](linux.md).
- **Linux packages.** `maximal` installs the bun-compiled `maximal` in `/usr/bin` plus a user systemd unit; `maximal-desktop` is the Tauri app built with `tauri.linux.conf.json` (binary `maximal-desktop`) and `bundle.externalBin: []`. The shell's `sidecar("maximal")` resolves to the file next to its own (canonicalized) executable, so the tray app runs the `maximal` package's `/usr/bin/maximal`, and `maximal-desktop` depends on exactly that version. The shell sets `HOST=127.0.0.1` on Linux as it does on every desktop platform, so the proxy listens on loopback only. Packaging and the apt repository live in `build/linux/`.
- **Shell-visible wire types live in `src/lib/config/settings-types.ts`** (zod) and the shell imports them (`shell/src/proxy/client.ts`). Don't hand-copy types into the shell.

## Plugins

Built-in plugins extend Maximal in-process. A plugin is a **connector** (it exposes tools to MCP clients at `/mcp/<id>` and gets host-managed tool permissions) an **extension** (no MCP endpoint, no client connections; Settings lists it with its enable toggle, status, actions and config form, but no endpoint or tool permissions; FigJam, `packages/plugin-figjam`, is the first) or a **model** plugin (`kind: "model"`: no MCP endpoint and no client connections like an extension, but Settings lists it with its enable toggle and config form; `packages/plugin-decisions`, `packages/plugin-systemone` and `packages/plugin-images` are the first, capability plugins that serve one model operation through a provider's models, on by default). Work IQ (`packages/plugin-workiq`, user guide [`workiq.md`](workiq.md)) is the first connector. Plugins are trusted in-process ESM modules run under [cordis](https://www.npmjs.com/package/@deepseek-ai/cordis) (`@deepseek-ai/cordis@4.0.2`); cordis scopes what a plugin registers to its lifetime but does not sandbox it.

- **Packages** (Bun workspaces, each with its own `test` and `typecheck`; `bun run plugins:test` / `plugins:typecheck` run them all). `packages/plugin-sdk` is the contract: the module shape, the manifest, the service interfaces on `ctx`, tool/status/permission types, and test helpers (`/testing`); its `./gateway` subpath is the cordis-free seam the app core uses. `packages/plugin-host` implements that gateway on cordis. Each plugin is its own package. `packages/connector-kit` turns a remote MCP server into a connector plugin from a manifest (`defineRemoteMcpConnector`): sign-in strategies (`entra`, `mcp-oauth`, `none`), upstream sessions with MCP version negotiation, a terms gate, setup status, and tool mirroring; its `./testing` export has a fake remote MCP server and an instant fake sign-in. Work IQ is built on it. See the SDK, host and kit READMEs.
- **Contract.** A plugin module exports `name` (the id: `/^[a-z][a-z0-9-]{1,31}$/`, also its MCP server name and storage directory), `manifest` (static JSON: `id` = `name`, `kind`, `displayName`, `description`, `homepage?`, `settingsVersion`, `configSchema?` for the Settings form, and for connectors `connector: { transport, endpoint, auth: { type, … }, terms? }` — public identifiers only, never secrets), `inject` (which of `tools`, `surface`, `storage`, `host` it uses), `Config` (a Standard Schema, zod 4 here, for which `{}` is valid), `apply(ctx, config)`, and optionally `migrateSettings(fromVersion, config)` and `defaultToolPermission(tool)`. `ctx.tools` registers MCP-shaped tools, `ctx.surface` sets the Settings status and backs its action buttons, `ctx.storage` is a private `<app dir>/plugins/<id>/` (0700, files written atomically with 0600; `settings.json` is reserved for the host), and `ctx.host` opens the system browser, logs through consola, reports the app version and the port Maximal serves on (`maximalPort()`, read when called). The host can provide more services: `createPluginHost({ services: { extra } })` takes `PluginServiceFactory` functions, `(root: Context, runtime: PluginRuntime) => Service`, each building a cordis `Service` on the root (`runtime.slotOf(this.ctx, "<name>")` identifies the calling plugin). Their names join the built-in four as valid `inject` entries (a name nobody provides is still refused with `missing-service`), and the SDK's `AppServices` interface is the declaration-merging hook that types them on `ctx` (`Context extends AppServices`). `compose.ts` provides one: `serverTools` (below).
- **Server tools.** A plugin that injects `serverTools` registers tools the model calls and Maximal runs itself in the `/v1/messages` loop: `ctx.serverTools.register({ name, description, input_schema, render, offer, clients?, execute(input, call) })` (name `/^[a-z][a-z0-9_]{0,63}$/`; the description is part of the prompt-cache prefix, so keep it fixed). `render` is `hidden` (the client sees the text around the call, never the call or its result) or an `anthropic-*` render, which only the built-in web tools use; a plugin tool with one is not offered. `offer` is `always` (for the `clients` it names, default `["claude-code"]`) or `when-client-declares` (needs an `anthropic-*` render). Registrations are bound to the plugin's fiber and names are unique across plugins (`duplicate-server-tool`). The gateway's `serverTools()` lists the active plugins' tools sorted by name and `callServerTool(pluginId, name, input, call)` runs one (a throw is an `isError` result; the host sets `call.budget` to `{ plugin, tool }`; the budget limits covering that pair are checked before `execute` runs and a refusal is the tool's result, see *Budget enforcement*). A billed tool also declares `estimate(input)` and calls `call.reportSpend(...)` (see *Budget enforcement*). Server tools are not MCP tools and take no part in tool permissions. `web_search` and `web_fetch` are not a plugin: they stay in core as a built-in provider on the same planning path (`src/routes/messages/web-tools/listings.ts`). The decisions and SystemOne plugins register `decide` and `classify` this way (hidden, `always`, free): each exists only while its binding's provider is signed in and offers the model, and a `tools.decide` / `tools.classify` config flag (default on) turns it off; they are not served over `/mcp/<id>`, which is connector-only. The images plugin (`packages/plugin-images`, [README](../packages/plugin-images/README.md)) registers `generate_image` and `edit_image` the same way (hidden, `always`, on by default; `generateImage` / `editImage` in its config turn each off). They dispatch the plugin's own `images.generations` / `images.edits` relay through the first binding's provider, save the pictures as files under `<app dir>/plugins/images/output/` (or `outputDir`; atomic, mode 0600) and answer with paths, never base64. `edit_image` reads only image files (absolute path, no `..`, image extension plus magic bytes, at most 20 MB, a symlink only within its own folder). The first billed call is refused until the person approves it (notification, tray `attention` and a Settings action; the SDK has no mid-call prompt for server tools); the approval is stored as `approval.json` in the plugin's storage. The planner and loop are described under *Request flow*.
- **Credentials.** A connector's sign-in (Entra / MCP OAuth tokens, accepted terms) lives in that connector's own `ctx.storage`, separate from Maximal's GitHub/Copilot credentials and from every other connector, and is never sent to MCP clients or Settings. The Settings API shows only the auth *type*. Entra's MSAL token cache is sealed (`packages/connector-kit/src/auth/sealed-cache.ts`): AES-256-GCM ciphertext in `msal-token-cache.sealed.json`, its key in the OS credential store via `Bun.secrets` (Keychain, Credential Manager, Secret Service; service `Maximal connectors`, entry `<id>/msal-token-cache/<key id>`). Only the 32-byte key goes there because Credential Manager caps a value at 2.5 KB. Store calls run off the event loop and wait at most 60 s; only that connector's token lookups wait on them, never plugin start-up, client sync, Settings or model traffic. Without a usable store the newest sign-in is kept in memory for the rest of the process, keyed by connector and data directory so turning the connector off and on keeps it, and the `ready` status says so; the sealed file is never deleted because the store failed. A refused call is retried after 5 minutes and the in-memory sign-in sealed once the store works; a call that gets no answer stops store use until restart and raises a `sign-in-not-saved` notice. MCP OAuth's state is sealed the same way (`oauth.sealed.json`, entry `<id>/mcp-oauth/<key id>`).
- **Attention.** A plugin that needs the person now sets `attention: { summary, actions }` on its status (`PluginStatus.attention`; each action is a normal `PluginStatusAction` backed by a registered action, with an id that stays the same for the same thing). `GET /settings/api/plugins/attention` (`src/lib/plugins/attention.ts`) lists `{ plugin, name, summary, actions }` for enabled, running plugins whose current status has it. The menu-bar shell polls it on the same 5 s loop as notices (`PluginAttention` in `sidecar_runtime.rs`): while anything is listed the tray icon is ATTENTION and the menu (macOS and Windows alike) starts with one item per action, `<plugin name>: <action label>` (the plugin's English label; no catalog string), that POSTs the existing `/settings/api/plugins/<id>/actions/<actionId>` and then re-reads the list so the item goes at once. FigJam uses it for pairing requests. The announcement itself stays a notice.
- **Notices.** `ctx.surface.notify({ code, message, params? })` raises a one-off message (gateway `notice` event). The serving process queues it with the plugin's name (`src/lib/plugins/notices.ts`, at most 20), the menu-bar shell takes the queue on its 5 s poll (`POST /settings/api/notices/plugins`) and shows one native notification each, worded by `code` in the user's language (`connected`, `sign-in-not-saved`) or else the plugin's English `message` (FigJam's `figjam-pair-requested` has no wording yet and shows its English message). The connector kit raises `connected` when a connector reaches `ready` from signed out or `error` (at most every 5 minutes; not on a start with a saved sign-in, nor on token refreshes).
- **Operation registry** (`operations` service, `packages/plugin-sdk/src/{operations.ts,runtime/operations.ts}`). `compose.ts` installs `operationsService` as an extra service. A plugin that injects `operations` calls `ctx.operations.register({ operation, bindings: [{ model, provider, upstreamModel }], handle })` for one of `MODEL_OPERATIONS` (`systemone`, `decisions`, `images.generations`, `images.edits`); the registration is withdrawn when its disposer runs or the plugin's fiber is disposed (disable, reload, shutdown). A second registration of the same `(operation, provider, upstreamModel)`, from any plugin, throws `PluginContractError` (`duplicate-operation`; a malformed one is `invalid-operation`). The app core reaches it through `gateway.operations()`, an `OperationDispatch`: `resolve(operation, model)` matches `"<provider>/<model>"` exactly and a bare model only when exactly one enabled binding serves it; `dispatch(request)` runs the handler with the resolved `binding` and throws `OperationUnavailableError` when nothing resolves (plugin off, unknown or ambiguous id); `servedModels()` lists what is served now; `subscribe(listener)` fires on every registration change. The pass-through routes use it (see *Pass-through routes*); a capability plugin's `bindings` are its `Config`, one `{ model, provider, upstreamModel }` per served model, and `relayOperation` / `responsesUsage` / `plainUsage` / `bindingsStatus` (`packages/plugin-sdk/src/relay.ts`) are the shared pieces of a plugin that relays one provider path unchanged. A plugin's status reflects its provider: `signin-needed`, `model-not-offered` (the catalog lacks the model, e.g. not on the plan) or `ready`. Tests use `createFakeUpstream` / `capabilityServices` from `@stuffbucket/maximal-plugin-host/testing`.
- **Provider registry** (`providers` service, `packages/plugin-sdk/src/{providers.ts,runtime/providers.ts}`; Copilot's implementation `src/lib/plugins/providers/copilot.ts`). `compose.ts` installs `providersService([createCopilotProvider()])`, so a plugin that injects `providers` gets `ctx.providers.get("copilot")` (also `list()` and `register(provider)`, which is bound to the plugin's fiber; an id that is taken throws `PluginContractError` `duplicate-provider`, a malformed provider `invalid-provider`). An `UpstreamProvider` supplies `postJson` (auth and transport; a refusal throws `HTTPError` whose `call` is `{ provider, endpoint, model }`), `model(id)` (catalog entry, undefined when the plan lacks it), `onCatalogChange`, `available`, `adviseError` (the upstream-error advice), `cost(reply)` (Copilot's `copilot_usage.total_nano_aiu`) and optional `quotaWindows()`. `composePluginGateway({ copilot: { sendRequest } })` injects the transport for tests. The decisions, SystemOne and images plugins reach Copilot through it (`ctx.providers.get(binding.provider)`).
- **Composition and boundary.** `src/lib/plugins/compose.ts` is the only `src/` module that imports the host, plugin packages, the connector kit, the SDK root or cordis (dependency-cruiser rule `plugins-only-via-composition-root`). It builds the host services and lists the built-ins; `composePluginGateway({ plugins, storageRoot, host })` is the override seam for tests and the connectors bench, which hand the result to `startPlugins({ gateway })` / `runServer({ pluginGateway })`. Nothing in production reads an override. Everything else in `src/` imports only `@stuffbucket/maximal-plugin-sdk/gateway` and reaches the running gateway through `src/lib/plugins/gateway.ts`; CLI commands have none.
- **Lifecycle** (`src/lib/plugins/runtime.ts`). After the listener binds, boot migrates `config.json`, cleans up old Claude Desktop entries, creates the gateway, moves legacy configs into settings files (below), runs `reconcile(config.plugins)` and syncs clients, detached from serving. `reconcile` gives each enabled plugin its own fiber: an unreadable settings file, an invalid config or a throwing `apply` marks only that plugin `failed`; disabling disposes the fiber and with it the plugin's tools, actions and status; a changed config reloads it; an unchanged failed one is retried only after toggling it off and on. Settings changes and `POST /_internal/reload` reconcile again. Shutdown closes the MCP sessions (`onPluginsStopping` hooks), then disposes the gateway within 1.5 s of the 2.5 s budget.
- **Config.** `config.json` → `plugins.<id>` is `{ enabled?, clients? }` (absent means off; `clients` is `["claude-code"]` or empty, connectors only). The plugin's own config lives in its **settings file** `<app dir>/plugins/<id>/settings.json` (host-owned, 0600, atomic writes): `{ "$schema": "maximal-plugin-settings/1", plugin, version, config, tools: { permissions, catalog } }`. On every start the host checks the envelope, runs `migrateSettings` when the stored `version` is older than `manifest.settingsVersion`, validates `config` with `Config` (failure ⇒ `failed` with a path-qualified error such as `workiq.endpoint: Invalid URL`) and writes back only after a successful migration; an unreadable, foreign or newer file fails that plugin and is never overwritten. Settings edits go through `gateway.updateConfig` (validate → write → reload). Migrations at boot: a legacy `plugins.<id>.config` in `config.json` is moved into the settings file once (`gateway.importLegacyConfig`; a file that already has a config wins) and then removed from `config.json` (kept when the settings file is unreadable, for the next boot); a missing `plugins.workiq` is migrated once from the parked broker's Work IQ endpoint (`mcpBroker.servers[]` with `catalog: "workiq"`): on only if the broker and the endpoint were, with its Claude Code choice. The `mcpBroker` block itself is accepted and left alone. The plugins that replaced always-on routes (`DEFAULT_ON_PLUGINS` in `src/lib/plugins/settings.ts`: `decisions`, `systemone`, `images`) are turned on at every boot where `plugins.<id>.enabled` has no value yet, so upgrading keeps `/v1/decisions`, `/v1/systemone` and `/v1/images/*`; a choice the user made is never overwritten.
- **Tool permissions** (connectors). Each tool is `allow`, `ask` or `block`. Effective permission: the user's choice in the settings file (`tools.permissions`) > the plugin's `defaultToolPermission` > the host default (`allow` for read-only tools, `ask` for the rest). Choices are kept by name for tools that disappear and re-apply when they return. Changing them never reloads the plugin. Settings groups tools by annotations: `readOnlyHint` ⇒ read-only, else `destructiveHint` ⇒ write/delete, else other. The gateway's `callTool` refuses a blocked tool, and an `ask` tool unless the call carries `approved` (set by the MCP layer below); both refusals are `isError` results naming the place in Settings to change it (`blockedToolText` / `unapprovedToolText` in the SDK's gateway module).
- **Catalog cache.** Whenever a plugin's registered tool set becomes non-empty, the host stores it with a timestamp in `tools.catalog`. Settings shows live tools when the plugin is active with tools (`toolsSource: "live"`), else the cached catalog (`"cache"`, with `catalogUpdatedAt`), else nothing (`"none"`), so permissions can be set while a connector is off or signed out. MCP listing always uses live tools only.
- **MCP projection** (`src/routes/plugins/`). `/mcp/<id>` serves an enabled connector's tools over Streamable HTTP with the MCP SDK's low-level server (`@modelcontextprotocol/server`). Sessions are stateful and in-process: one server per `initialize`, closed on `DELETE`, when the plugin is turned off, or after 30 minutes with no request or open stream (at most 64 at once; the oldest idle one makes room). `tools/list` reads the gateway: every live tool (empty while a connector is starting or needs setup). A blocked tool stays listed with its description prefixed by "… is turned off in Maximal. To use it, turn it on in Maximal → Settings → … → Tool permissions.", so the model can tell the person why; an `ask` tool carries `_meta["anthropic/requiresUserInteraction"]: true`, which makes Claude Code confirm every call; `notifications/tools/list_changed` follows the gateway's `tools` (registrations and permission changes) and `lifecycle` events, debounced 100 ms. `tools/call` passes the request's abort signal, the session id, progress (when the client sent a progress token) and elicitation (when the client declared it, 2025-era push requests). A call to an `ask` tool needs approval first: Claude Code's own per-call prompt counts (client `claude-code`); any other client that declared elicitation gets a field-less form ("Maximal: allow <connector> to run <tool>?" with the arguments), and only *accept* runs the tool (decline, cancel or a failed elicitation is an `isError` result saying it wasn't run); a client without elicitation is refused with the `unapprovedToolText`. A blocked tool answers with the `blockedToolText`; a tool that throws is an `isError` result; a connector that isn't running, or a tool called while the connector needs setup or is in error, answers an `isError` result naming its status; otherwise an unknown tool is a JSON-RPC invalid-params error. Auth: loopback only, no foreign `Origin` (403), then the main port's key rules; unknown or disabled plugins, extensions and model plugins are 404 `MCP_ENDPOINT_NOT_FOUND`.
- **Client sync** (`src/lib/plugins/clients/`). A connector's endpoint is registered with Claude Code while it is on, the user chose Claude Code for it, the Claude Code routing intent is on (`apps.claudeCode.enabled`), and Claude Code doesn't already have its own: a server or enabled plugin named `<id>` (`standalone` on the Settings client view, shown as a notice on the connector). Entries go into Claude Code's user scope (`~/.claude.json`, or `$CLAUDE_CONFIG_DIR/.claude.json`) as `maximal-<id>` → `{ type: "http", url: "http://127.0.0.1:<port>/mcp/<id>", headers }` with the real key, so Work IQ's tools are `mcp__maximal-workiq__*`. Maximal writes the file itself (no `claude` CLI): one verified atomic write per pass, retried because Claude Code rewrites the file, and only when something differs. An entry is Maximal's when its name is `maximal-<id>` and it points at `/mcp/<id>` on 127.0.0.1, any port; nothing else is touched, and an unreadable file is never replaced. `syncPluginClients()` is the only way in, synchronous and idempotent, and acts only in the serving process: boot, plugin settings changes, the Claude Code toggle, API key changes and Settings reads (which catch up with edits made in Claude Code) all call it. Entries stay while Maximal is stopped (Claude Code shows `maximal-<id>` failing to connect); `maximal uninstall` removes them. Names an older version recorded in `apps.claudeCode.mcpServers` (it named entries `<id>`) are removed on the first pass, then the record. Claude Desktop is not synced (its MCP entries needed the parked broker's stdio adapter): at boot Maximal removes the Desktop entries it recorded (`apps.claudeDesktop.mcpServers`) that run `maximal-mcp-broker[.exe]`, then clears that record.
- **Settings API** (`src/routes/settings/plugins.ts`; wire schemas in `src/lib/config/settings-types.ts`). `GET /settings/api/plugins` → `{ plugins: PluginView[] }`: id, kind, `source: "built-in"`, display fields, the public manifest subset (for connectors `connector: { transport, endpoint in effect, auth: { type }, terms? }`), `enabled`, `lifecycle`, `error?`, `status?`, `toolCounts: { total, byGroup }`, `toolsSource`, `clients` and `endpoint` (both empty for non-connectors). `GET /settings/api/plugins/:id` → `PluginDetailView`: the list item plus `settingsVersion`, `config?`, `configSchema?`, `tools` (full schemas, `group`, `permission`, `permissionSource`) and `catalogUpdatedAt?`. `PATCH /settings/api/plugins/:id` `{ enabled?, clients?, config? }` writes `config` first (rejected ⇒ 400 with `issues: [{ path: "config.<field>", message }]`, nothing changed), then persists `enabled`/`clients`, reconciles, syncs clients and returns the detail. `PUT /settings/api/plugins/:id/tool-permissions` `{ permissions: { <tool>: "allow" | "ask" | "block" | null } }` (`null` clears) → detail; a malformed body is a 400 with `issues`. `POST /settings/api/plugins/:id/actions/:actionId` answers `202 { ok: true }` once the plugin accepts the action (404 unknown plugin or action, 409 not running); the action runs on and reports through status. 404 for an unknown plugin everywhere, 409 when its settings file can't be read. Views are built field by field, so auth client ids, authorities and scopes never leave the server. The events stream sends `plugins.changed` (same shape as the list) on connect and, debounced, on every gateway event (lifecycle, status, tools, settings) and settings change.
- **Status.** `/status` → `subsystems.plugins: { active, failed }` (counts only).
- **Bench.** `bun run bench:connectors` (`scripts/bench/`) runs the real server (`runServer`) with the real Work IQ connector against the kit's fake MCP server seeded with the Work IQ fixture and a fake sign-in, in a throwaway user environment; `--drive` scripts an MCP client session and prints a pass/fail table. `tests/bench-connectors.test.ts` runs the same drive in-process. See [`commands.md`](commands.md).
- **Testing.** `@stuffbucket/maximal-plugin-host/testing`: a lifecycle harness (real host, temp settings files, an ordered transcript of everything crossing the plugin boundary) and `runPluginConformance`, which every plugin package runs. `tests/e2e-plugin-lifecycle.test.ts` walks Work IQ through its whole lifecycle in the real app against a golden transcript. See the SDK README and [`dev/testing-strategy.md`](dev/testing-strategy.md).

## Parked MCP broker

The generic MCP broker (broker binary, supervisor, stdio adapter, its client sync, elicitation Requests, Claude Desktop sync, Work IQ via the `workiq` CLI) is parked under `parked/mcp/`: kept in git, excluded from build, typecheck, lint, tests, CI and packaging. See [`parked/mcp/README.md`](../parked/mcp/README.md). Installers and the updater still stop and remove a `maximal-mcp-broker` left by an older version.

## Token counting

`/v1/messages/count_tokens`: when `anthropicApiKey` is configured, forwards Claude model requests to Anthropic's free `/v1/messages/count_tokens` endpoint for exact counts. Otherwise falls back to GPT `o200k_base` tokenizer with 1.15x multiplier (`src/lib/models/tokenizer.ts`).
