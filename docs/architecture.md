# Architecture

**This repo does not contain the proxy engine.** It packages and distributes it,
and it hosts the desktop client and the website.

The engine — routing, middleware, model dispatch, config, the token store,
diagnostics — lives in [`stuffbucket/maximal-core`](https://github.com/stuffbucket/maximal-core)
and is consumed here as a git dependency (`@stuffbucket/maximal-core`). For
anything about how a request is handled, read that repo's
[`docs/architecture.md`](https://github.com/stuffbucket/maximal-core/blob/main/docs/architecture.md);
this document deliberately does not mirror it, because the mirrored copy drifted
badly enough to be worse than no copy at all.

`src/` was removed from this repo in #442.

## What lives where

| Path | Purpose |
|---|---|
| `client/` | Electron 43 + React 19 + TypeScript + Vite desktop app, **managed by npm, not Bun**. Compiles the engine into its own sidecar via `client/scripts/build-core.ts`; everything else (install, typecheck, test) runs through npm. Has its own CI workflow, `.github/workflows/client-ci.yml`. |
| `site/` | Astro website, deployed to GitHub Pages. **Deploys are currently frozen** — see *Site and Pages* below. |
| `scripts/` | Release and packaging tooling: `sync-homebrew-formula.ts`, `write-updates-manifest.ts`, `sbom.ts`, `secret-scan.sh`, plus `scripts/dev/verify-build.ts`. |
| `build/` | Distribution templates — `build/homebrew/` and `build/macos/`. |
| `tests/` | Tests for the packaging and distribution surface only (manifests, the Homebrew formula renderer, the macOS installer template, `verify-build`). Bun's built-in runner. |
| `i18n/` | Translation catalogs (`i18n/catalogs/`) and their parity checks. See [`i18n/README.md`](../i18n/README.md). |
| `contrib/` | Contributor-facing extras (`contrib/debug/`). |
| `reports/` | Recorded performance baselines. Historical data, not regenerated by CI. |
| `docs/`, `research_log/` | This documentation and dated investigation notes. |

## Building and shipping the CLI

The published package is `@stuffbucket/maximal`, exposing one binary,
`maximal` → `./dist/main.js`, and shipping only `dist/`.

The build compiles the engine's entry point straight out of `node_modules`:

```sh
bun build node_modules/@stuffbucket/maximal-core/src/main.ts --target=bun --outdir dist
```

`dev` and `start` run that same path directly rather than the built output.
`prepack` runs `build`, so the compiled `dist/` is produced at publish time.

Two consequences worth knowing before changing packaging:

- **The engine is consumed as source, not through its package exports.** Three
  root scripts path into `node_modules/@stuffbucket/maximal-core/src/main.ts`.
  That works, but it means the installed tree's layout is load-bearing — a
  package manager that does not produce a flat, npm-shaped `node_modules` will
  break the build.
- **`client/` is a separate install root on npm**, and
  `client/scripts/build-core.ts` reads the resolved maximal-core git SHA out of
  `client/package-lock.json` by its npm-specific shape. Changing the client's
  package manager means rewriting that version stamping.

## Electron client

`client/` is the desktop app for non-CLI users — `npm install`,
`npm run typecheck`, `npm run test:run` (Vitest), `electron-forge` for
packaging. Bun is used only to compile the engine into a sidecar binary via
`client/scripts/build-core.ts`. See
[`dev/testing-strategy.md`](dev/testing-strategy.md) §1/§3 for how the two test
suites (root `bun test` vs. `client/`'s Vitest) relate.

The Tauri menu-bar shell that previously filled this role was retired in #442;
`shell/` no longer exists.

## Site and Pages

`site/` builds to `site/dist` and publishes to GitHub Pages via
`.github/workflows/deploy-pages.yml`, the only workflow with a path to Pages.

**Automatic deploys are frozen** as of #447. The `push` trigger is commented out
*and* the workflow is disabled at the Actions level, so neither a push nor a
`workflow_dispatch` will run it. Resuming requires both: restore the `push:`
block and `gh workflow enable deploy-pages.yml`. The file says so at the top.
Note that the trigger's paths filter covers the workflow file itself, so the
commit that restores it will itself deploy.

## Parallel-agent convention

This repo can collide on a shared working tree (lint-staged stash + concurrent
merge ate a turn already). For parallel agents:

- **Spawned subagents:** pass `isolation: "worktree"` to the Agent tool.
- **Sessions:** create a worktree manually with
  `git worktree add ../maximal-<task> -b agent/<task>`; clean up with
  `git worktree remove ../maximal-<task>` after merging back. `git worktree add`
  does **not** run `bun install`, so run it in the new tree if you need its
  `node_modules`.
- **Never run `git stash pop` in a shared working tree.** It silently merges
  another in-flight worker's stash into your tree, and on conflict it leaves an
  inconsistent state that's easy to "clean up" by `rm`-ing files that aren't
  yours. We lost a session's worth of React-shell work to this exact path: a
  subagent ran `git stash pop` to bisect a test failure, hit a conflict, and
  `rm`'d untracked files it didn't recognize. If you need an isolated bisect,
  use a worktree (see above). If you must inspect a stash, use
  `git stash show -p stash@{N}` (read-only) and never `pop` / `apply` outside an
  isolated tree.
- **Worktrees are cheap on disk.** Bun installs with copy-on-write clones on
  macOS, so a second `node_modules` costs single-digit MB of real disk even
  though `du` reports the full size. Do not use `du` to decide whether a
  worktree is expensive.

See also: `docs/codegen-feedback-loops-practices.md` → Dispatch and review loops.

## Testing

`bun test` at the root covers the packaging and distribution surface, and
nothing else — the engine's own suite lives in maximal-core and runs there.

The `mock.module` leak guidance that used to live here went with `src/`. The
`mockModuleLeakGuard` ESLint rule it described no longer exists in
`eslint.config.js`, and no test in this repo mocks a module. If you are chasing
a cross-file mock leak, you are almost certainly in maximal-core — see its
testing docs.

Still true here:

- **Green tests can still test nothing.** For security-critical or branchy
  logic, confirm the test actually exercises the branch it claims to. See
  [`dev/testing-strategy.md`](dev/testing-strategy.md) §6 for the disposition
  rule. Note that the root `mutate` script was removed with the excavation;
  mutation testing now belongs to whichever repo owns the code under test.

## Release & PR conventions

- **Release is driven by Conventional Commit *types*.** release-please scans
  commits since the last tag; only `feat:` (minor) and `fix:` (patch) cut a
  release. `test:`/`chore:`/`ci:`/`docs:`/`refactor:` are release-silent. If
  release-please "isn't doing anything," it almost certainly found no
  `feat`/`fix` commit — check the `release-pr` step log for
  `No user facing commits found ... skipping` before assuming it's broken.
- **Squash-merge uses the PR *title* as the commit subject.** So the PR title
  must be a single valid Conventional Commit (`fix: …`, not `test+fix: …`). A
  non-standard type like `test+fix` parses as one unrecognized token and
  release-please skips it — even if the diff contains a real `fix:`. Title PRs
  accordingly; the body's individual commit messages don't reach `main` through
  a squash.
- **Branch protection requires branches to be up to date before merging.** A
  merge to `main` puts every other open PR `BEHIND`; update with
  `gh pr update-branch --rebase` and wait for CI before merging the next one.
